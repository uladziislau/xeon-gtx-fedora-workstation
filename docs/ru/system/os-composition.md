## Введение

Вопрос простой: **можно ли сегодня собрать операционную систему из лучших доступных открытых компонентов — так же, как собирают ПК из деталей от разных производителей?**

Ответ: **да, но с оговорками.** Полностью «своя» ОС — это огромный труд (тысячи человеко-лет). Но ОС — это **композиция слоёв**. Каждый слой можно заменить на лучший из доступных, если это позволяет экосистема.

Данный документ описывает **концептуальную композицию** — «что из чего состоит» и «что на что можно заменить», без обязательств что-либо менять.

## Архитектура ОС: слои от железа до пользователя

```
┌─────────────────────────────────────────────────────────────┐
│  Уровень 8: Пользователь (приложения, DE, браузер)          │
├─────────────────────────────────────────────────────────────┤
│  Уровень 7: Пользовательская среда (KDE, Hyprland, shell)   │
├─────────────────────────────────────────────────────────────┤
│  Уровень 6: Графика (Wayland, X11, драйверы GPU)            │
├─────────────────────────────────────────────────────────────┤
│  Уровень 5: Системные сервисы (сеть, звук, логи, время)     │
├─────────────────────────────────────────────────────────────┤
│  Уровень 4: Init / PID 1 (systemd, OpenRC, dinit)           │
├─────────────────────────────────────────────────────────────┤
│  Уровень 3: Ядро (Linux, CachyOS, Zen, Redox)               │
├─────────────────────────────────────────────────────────────┤
│  Уровень 2: Initramfs (dracut, booster, mkinitcpio)         │
├─────────────────────────────────────────────────────────────┤
│  Уровень 1: Загрузчик (GRUB2, systemd-boot, Limine, rEFInd) │
├─────────────────────────────────────────────────────────────┤
│  Уровень 0: Прошивка (UEFI/BIOS, openSIL, u-root)           │
└─────────────────────────────────────────────────────────────┘
```

Каждый уровень имеет **интерфейсы** с соседними. Заменяемость уровня определяется тем, насколько стандартны эти интерфейсы.

## Уровень 0 — Прошивка (Firmware)

### Что это
Код, который работает **до** загрузчика: инициализация памяти, чипсета, диска, вывод логотипа.

### Стандарты
- **UEFI** (замена BIOS, с 2012+) — стандарт де-факто
- **UEFI Secure Boot** — цепочка доверия от прошивки к ядру
- **ACPI** — таблицы описания железа (ACPI tables)
- **SMBIOS / DMI** — информация о железе

### Лучшее сегодня
| Компонент | Что это | Статус |
|-----------|---------|--------|
| **coreboot** | Свободная замена проприетарной прошивки | Только для серверов/некоторых плат |
| **openSIL** | Открытый начальный загрузчик AMD System Init Library | AMD только, новое |
| **u-root** | Загрузка через Go-совместимый "рыжик" | Экспериментально |

### Вердикт
Прошивку своей материнской платы (Xeon E5-2696 v3, вероятно C602/Huananzhi/Supermicro) **не заменяешь** — coreboot для этих плат практически не существует. Принимаем UEFI как данность.

## Уровень 1 — Загрузчик

### Что это
Код, который находит ядро и initramfs на диске, загружает их в память и передаёт управление.

### Базовые этапы работы загрузчика

```
1. Прошивка находит ESP (EFI System Partition, FAT32)
2. Загрузчик (например, systemd-boot) читает /boot/loader/entries/*.conf
   └── тип записи: linux, initrd, options
3. Загружает ядро (vmlinuz-*) и initramfs (initrd.img-*)
4. Передаёт управление ядру с параметрами (cmdline)
5. Ядро распаковывает само себя, монтирует initramfs, запускает init
```

### Кандидаты

| Загрузчик | Язык | Плюсы | Минусы | Сложность |
|-----------|------|-------|--------|-----------|
| **GRUB2** (текущий) | C | Всё умеет: themes, snapshots, multi-boot | Медленный, сложная конфигурация | — |
| **systemd-boot** | C | Минимальный, быстрый, читает .conf-файлы | Без тем, только UEFI | Низкая |
| **Limine** | C | Современный, быстрый, гибкий | Растущая, но малая аудитория | Средняя |
| **rEFInd** | C | Красивый, автообнаружение | Сложный | Средняя |
| **barebox** | C | Для встраиваемых систем | Не для десктопа | — |

### Рекомендация для SEOS QST
**systemd-boot** — если не нужны темы и мультизагрузка. Он минимален и управляется текстовыми файлами:
```ini
# /boot/loader/entries/seos-7.1.7.conf
title   SEOS QST 7.1.7
linux   /vmlinuz-7.1.7-cachyos1.fc44.x86_64
initrd  /initramfs-7.1.7.img
options root=UUID=... rootflags=subvol=root rw
```

## Уровень 2 — Initramfs

### Что это
Минимальная корневая ФС в памяти. Ядро не умеет само читать Btrfs/LUKS/NVMe — initramfs содержит **модули и утилиты**, чтобы: смонтировать реальный корень, расшифровать LUKS, загрузить NVIDIA-модуль и т.д.

### Кандидаты

| Генератор | Язык | Размер | Скорость | Особенности |
|-----------|------|--------|----------|-------------|
| **dracut** (текущий) | Bash/C | 40–60 МБ | Средняя | Модульный, стандарт Fedora/RHEL |
| **booster** | Go | 15–25 МБ | Быстрая | Минимализм, использует host-модули |
| **mkinitcpio** | Bash | 20–30 МБ | Средняя | Arch-стандарт |
| **early userspace** | C | 5–10 МБ | Очень быстрая | Полностью ручная сборка |

### Вердикт
**booster** — лучший современный генератор: он быстрее (Go, параллелизм), компактнее, и сгенерированный образ чисто декларативен (`/etc/booster.yaml`). Но замена требует: установить booster, перегенерировать initramfs, проверить загрузку, сохранить старый образ как fallback.

## Уровень 3 — Ядро

### Что это
Главный код ОС: планировщик, драйверы, виртуальная память, сетевой стек, файловые системы. Всё остальное — пользовательский слой поверх ядра.

### Кандидаты

| Ядро | База | Особенности | Применимость |
|------|------|-------------|--------------|
| **Linux (mainline/vanilla)** | — | Универсальное, огромная поддержка | Всегда рабочий вариант |
| **CachyOS kernel** (текущий) | Linux + патчи | BORE-планировщик, оптимизации, sparse-index | ✅ Уже используется |
| **Zen / Liquorix** | Linux + патчи | Низкая латентность для десктопа | Хороши для интерактива |
| **Redox OS** | Свой (Rust) | Полностью на Rust | ⚠️ Экспериментально, не готово для десктопа |
| **FreeBSD** | Своё | Не Linux, своя лицензия | Другая экосистема |

### Планировщики CPU (scheduler)
- **EEVDF** — стандартный в Linux 6.6+ (честная виртуальная дедлайн-модель)
- **BORE / sched-ext (scx)** — **уже используется** на этой машине (`scx_loader`)
- **SCHED_EXT** — фреймворк для BPF-планировщиков (scx_lavd, scx_rusty — Rust!)

### Вердикт
Ядро Linux — это **уровень с наибольшей совокупной мощностью**. Полностью на Rust (Redox) — интересно, но не готово. Практичный путь: **оптимизированное ядро Linux** (CachyOS/vanilla) + **BPF-планировщик** под нагрузку.

## Уровень 4 — Init / PID 1

### Что это
Первый процесс, который запускает всё остальное. Отвечает за: запуск сервисов, сбор зомби, cgroups, управление журналом, логин-менеджмент.

### Кандидаты

| Init | Язык | Экосистема | Используют |
|------|------|-----------|------------|
| **systemd** (текущий) | C | Огромная | Fedora, Ubuntu, Arch, Debian |
| **dinit** | C++ | Компактная, но растёт | Artix (опция), энтузиасты |
| **OpenRC** | C/Shell | Классическая | Gentoo, Alpine, Artix |
| **s6 / s6-rc** | C | Минимальная | Artix, Void (опция) |
| **runit** | C | Очень простая | Void Linux |
| **Shepherd** | Guile/Scheme | GNU-экосистема | Guix |

### Вердикт
systemd — **компромисс**. Он «непроизносимо большой», но именно его API используют все DE (logind, journald, resolved). Замена init на Fedora = **фундаментальная, многомесячная работа**. 

**Однако**: systemd — это **композиция компонентов**, и отдельные его части заменяемы:
- `systemd-resolved` → `unbound` / `dnsmasq`
- `systemd-journald` → `rsyslog` / `syslog-ng`
- `systemd-networkd` → `NetworkManager` (уже используется)
- `systemd-timesyncd` → `chronyd`

| apk | Alpine | Минимальный | Не для Fedora |

### Декларативность на Fedora: пути

**Путь A — Nix-слой поверх Fedora:**
```
Fedora (dnf) ────── системные пакеты
        └── Nix ── пользовательские приложения (home-manager)
```
Плюс: не трогаем ОС. Минус: параллельный мир.

**Путь B — rpm-ostree (Silverblue-стиль):**
```
ostree commit ── атомарный образ ── откат ребазированием
```
Плюс: иммутабельность. Минус: Fedora Workstation не заточена под это.

**Путь C — osbuild / Image Builder (Blueprints):**
```
blueprint.toml ── osbuild ── кастомный ISO/OSTree
```
Плюс: можно **собрать свой образ SEOS** и ставить его на другие машины.

## Файловая система и устойчивость к сбоям

### Текущая схема
```
nvme0n1 (Btrfs) ── / и /home, подтома, snapshots
sda (SATA SSD)  ── /boot, EFI (fallback)
zram0           ── swap (сжатая RAM)
```

### Кандидаты
| ФС | Плюсы | Минусы |
|----|-------|--------|
| **Btrfs** ✅ | Снапшоты, send/receive, чекисома, сжатие | Фрагментация (спорно) |
| ZFS | Мощные снапшоты, scrub | Лицензия CDDL (несовместима с ядром формально) |
| ext4 | Простая, зрелая | Нет снапшотов |
| F2FS | Оптимизирована для flash | Для телефонов/SSD |

## Отдельная глава: Отказоустойчивая ОС на Rust

### Вопрос
> Можно ли собрать абсолютно отказоустойчивую ОС: питание прерывается — система гаснет; питание появляется — возобновляется **с того же места**, будто ничего не было?

### Короткий ответ
**Да, но «с того же места» — это не «с того же инструкции».**

### Что технически означает «возобновление с того же места»

Есть несколько градаций:

#### 1. Файловая система не теряет данные (уже достигнуто)
```text
Btrfs: copy-on-write, чекисомы, журналы
Atomic writes: приложения пишут через rename() (A → B атомарно)
```
При резком отключении питания Btrfs восстанавливается за секунды. **Данные не теряются** на уровне ФС.

#### 2. Состояние приложений сохраняется (достижимо)
```text
systemd + диспетчер состояний:
- Firefox/Session Manager → восстановление вкладок
- Vim/Neovim persistent undo
- tmux → tmux-resurrect / continuum (восстановление сессий)
- Postgres: crash recovery (WAL)
```

#### 3. Состояние системы «продолжается как ни в чём не бывало» (почти достижимо)
```text
Сон в RAM (suspend-to-RAM) — питание не должно пропасть (RAM стирается)
Сон на диск (hibernate/suspend-to-disk) — работает уже 30 лет
Контейнеры/ВМ с чекпоинтом:
    CRIU (Checkpoint/Restore In Userspace) — заморозить процесс,
    сохранить дамп, перезапустить на другой машине!
```

#### 4. «С того же машинного кода» (невозможно полностью)
```text
CPU при включении начинает с RESET-вектора.
Продолжить выполнение с прерванной инструкции невозможно — 
например, операция записи могла быть на половине пути.
Но: журналы (WAL) и COW гарантируют, что "полузапись"
никогда не остаётся видимой. Это и есть "как будто ничего не было".
```

### Насколько Rust помогает?

**Rust решает другой класс задач:**
```text
C --- use-after-free, null pointers, data races → зависания, краши
Rust --- владение + borrow checker → исключает эти классы багов на этапе компиляции
```

Для **отказоустойчивости при отключении питания** главное не язык, а:
1. **Атомарность записи** (COW, WAL)
2. **Журналирование** (redundancy)
3. **Дамп состояния** (checkpoint)

### Существующие Rust-проекты (проверено на GitHub, август 2026)

| Проект | Что делает | Зрелость |
|--------|-----------|----------|
| **Redox OS** | Полная ОС на Rust (ядро, драйверы, userspace) | Активен, работает в VM и на железе |

## Глава 13.1 — Глубоко: что уже реально существует на GitHub

### Redox OS — «полная ОС на Rust»

Это **не «игрушечное» ядро**, а **полноценная ОС** с собственным userspace:

```
Redox OS (микроядро)
├── kernel                   — микроядро на Rust (осн. @jackpot51)
├── base                     — системные компоненты и драйверы
├── redoxfs                  — своя файловая система на Rust
├── relibc                   — C-библиотека на Rust (POSIX)
├── ion                      — shell на Rust
├── orbital                  — дисплейный сервер + WM (X11-подобный)
├── COSMIC                   — DE от System76 (rust-based)
└── pkgutils                 — пакетный менеджер
```

**Ключевые факты:**
- Лицензия MIT
- **Microkernel-архитектура** (вдохновлена seL4, MINIX, Plan 9, Linux, BSD)
- Есть **hardware compatibility** — поддерживает реальное железо
- Можно **запустить в VM** уже сегодня
- Ядро **не является Linux** — отдельная экосистема

**Важный нюанс:** Redox запускает COSMIC (Rust-DE от System76). То есть связка «Rust-ОС + Rust-десктоп» — **уже существует**.

### Theseus OS — fault recovery без избыточности

Академический проект (Cornell и др.), исследовательский. Ключевая идея — **intralingual design**: перенести управление ресурсами из рантайма в компилятор Rust.

```
Theseus OS
├── Ядро разбито на "crates" вместо "все в одном месте"
├── Live evolution — замена компонентов на лету
├── Fault recovery — восстановление после сбоев без рестарта
└── Нет сложных глобальных структур (нет единой кучи, PID-таблиц)
```

**This прямо отвечает на твой вопрос про «отказоустойчивость»:** This проект изучает восстанавливаемость **без дублирования** — то есть ближе всего к идее «упал-встал-продолжил».

### R3-OS — Rust RTOS для встраиваемых систем

```
R3 — static RTOS
├── Все объекты ядра определяются статически (compile-time)
├── Нет внешних build-тулов, только Rust compiler
├── Типы защищают доступ: safe code не может получить объект, ей не принадлежащий
└── Для embedded (MCU), не для десктопа
```

### Rust-for-Linux — Rust внутри Linux

Не отдельная ОС, а **Rust-подсистема в ядре Linux**:
```
Linux 6.x
├── drivers/gpu/drm/...     — Rust-драйверы
├── security/               — Rust-модули безопасности
├── fs/                     — Rust-файловые системы (ext2, btfrs-части)
└── samples/rust/           — примеры
```
Rust-код в ядре гарантирует **отсутствие memory-safety багов** там, где это критично.

### Hobby-ОС на Rust (для обучения)

Существует **огромное** комьюнити учебных ОС:
- **r3-os** (статич. RTOS)
- **LemonOS**, **zermia** и десятки других
- Книга **"Writing an OS in Rust"** (Философ) — стандарт входа
- crates: `bootloader`, `x86_64`, `uart_16550`, `spin`, `vga_buffer`

## Глава 13.2 — Реально ли собрать рабочую Rust-ОС сегодня для десктопа?

### Краткий ответ: **нет, для повседневного десктопа — ещё нет.**

| Слой | Redox сегодня | Linux сегодня |
|------|---------------|---------------|
| Ядро | Работает в VM на совместимом железе | Всё железо |
| GPU-драйвер (GTX 1660) | ❌ Нет NVIDIA | ✅ Проприетарный |
| 165 Гц Wayland | ❌ Нет | ✅ KWin Wayland |
| Приложения | Редкие | Всё |
| Браузер | Ограниченный | Chromium/Firefox |

### Почему это не «абсурд»

Хотя Redox не заменит рабочий десктоп, **ниша есть**:
- **For hobby/education** — огромная ценность (ты учишься даже больше, чем на Linux)
- **For embedded** — R3 и подобные уже практичны
- **For research** — Theseus уже публикует, изучает fault recovery

### Реалистичный сценарий для SEOS QST

```text
Не собирать всю ОС с нуля на Rust.
А использовать Rust-компоненты внутри привычной Fedora:

┌── SEOS QST (Fedora, CachyOS kernel) ──────────┐
│  uutils-coreutils (Rust ls/cp/rm)              │
│  fd, rg, bat, dust, zoxide (Rust утилиты)      │
│  scx_rusty (Rust-планировщик) ✅ уже есть      │
│  cosmic (опционально как DE-эксперимент)       │
│  ripgrep вместо grep                           │
│  Nushell (Rust shell, опция)                   │
└────────────────────────────────────────────────┘
```

То есть: **Rust-решения внедряются в систему по частям**, а не всей ОС целиком. Это даёт:
- Memory-safety в критичных местах
- Современный инструментарий
- **Ноль риска для загрузки**

## Глава 13.3 — Живая ОС: Rust + «возобновление как ни в чём не бывало»

### Ключевая мысль

Твоя идея «отключили питание — гаснет; включили — продолжил с того же места» — это **не фантастика**, а **комбинация существующих механизмов**:

| Механизм | Что делает | Где работает |
|----------|-----------|--------------|
| **CRIU** | Дамп процесса → восстановление (сеть, сокеты, память) | Linux, уже зрелый |
| **Btrfs COW** | Запись атомарна, partial write невозможен | Linux ✅ |
| **WAL / журналы** | Базы данных восстанавливают состояние | PostgreSQL ✅ |
| **Hibernate** | Вся RAM → диск, отработка после включения | Linux ✅ |
| **Theseus** | Восстановление без дублирования | Research |

### Как бы выглядела «идеальная» архитектура

```
APP (в контейнере) ── периодические CRIU-чекпоинты (из memory-safe Rust-демона)
SRV (systemd) ── завязан на аппаратный watchdog
FS (Btrfs) ── COW + checksums, scrub после аварии
HW (GTX 1660) ── момент отключения невидим для приложений
```

**План восстановления после внезапного отключения питания:**
```text
1. UEFI → systemd-boot → ядро (за 3–8 секунд)
2. Btrfs автоматически чинит при монтировании
3. systemd запускает сервисы (post-fail detection)
4. CRIU-сервис проверяет: был ли чекпоинт? → восстановить контейнер
5. tmux-resurrect / browser session → восстановить сессии
6. Пользователь продолжает работу (потеряно: < 1 минута)
```

Это **уже делаемо на сегодняшней Fedora** — вопрос только в настройке и автоматизации.

### Почему Rust здесь важен

Rust-код в критичных местах (CRIU-подобные демоны, планировщик, сетевой стек) **устраняет целый класс багов еще до запуска**:
- Нет use-after-free (нельзя разыменовать освобождённую память)
- Нет data races (компилятор не даёт)
- Нет null pointer dereference (Option вместо null)

Именно поэтому **Linux принимает Rust-драйверы**, а Redox/Theseus выбрали Rust как основу.

**Итог главы:**
> Полноценная Rust-ОС для десктопа — **не абсурд**, но и не готовый инструмент: Redox реален и работает, Theseus изучает fault recovery, R3 практичен для embedded. Практичнее всего — **внедрять Rust-компоненты в текущую Fedora частями**, а идею «возобновления» реализовать через CRIU + Btrfs COW + hibernate — уже сегодня.

## Выводы

1. **Полностью «свою» ОС с нуля** — задача на годы, но **слоистую композицию** из лучшего сегодня — да, можно собрать сегодня.

2. **Практичная стратегия:** не менять фундамент (ядро Linux, systemd, glibc), а:
   - **заменять модули** (firewalld → nftables, dracut → booster, GRUB → systemd-boot)
   - **выкидывать лишнее** (X11, PulseAudio, лишние локали, неиспользуемые сервисы)
   - **добавлять декларативность** (Nix-слой поверх Fedora)

3. **ОС на Rust со «сквозным возобновлением»** — возможно как **концепт комбинации** уже существующих механизмов: COW-ФС + журналы + чекпоинты (CRIU) + hibernate. Rust здесь даёт надёжность кода, но «продолжение с той же инструкции» физически невозможно; «продолжение с того же состояния» — достижимо уже сегодня.

4. **Следующий шаг проекта SEOS QST:** не принимать решений о заменах, а провести **аудит зависимостей** (что реально тянет за собой X11, firewalld, PulseAudio) — тогда решения станут взвешенными.
