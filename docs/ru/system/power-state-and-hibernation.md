## 1. Состояния питания (ACPI S-states)

ACPI описывает уровни сна от S0 до S5:

| Состояние | Название | RAM | CPU | Пробуждение |
|-----------|----------|-----|-----|-------------|
| **S0** | Работа | ✅ | ✅ | — |
| **S1** | Standby | ✅ | отключён от работы | ~секунды |
| **S2/S3** | Suspend-to-RAM | ✅ | выключен | ~секунды |
| **S4** | **Hibernate (Suspend-to-disk)** | ❌ сохраняется на диск | выключен | **~десятки секунд** |
| **S5** | Выключен | ❌ | ❌ | обычная загрузка |

В Linux поверх этих состояний:
- **s2idle** — «свободная» версия S3 (freeze userspace, CPU в глубоком C-state)
- **deep** — настоящий S3 (полный suspend-to-RAM)
- **disk** — S4 (hibernate)

## 2. Что такое hibernate (S4) и почему он «медленный»

### Как работает классический hibernate

```text
1. Ядро замораживает пользовательский слой
2. Копирует ВСЮ RAM в файл подкачки (swap)
   └── на этой машине 64 ГБ RAM → 64 ГБ записи на диск!
3. Выключает питание
4. При включении: загрузчик → ядро (обычная загрузка)
5. Ядро видит resume=UUID → загружает образ RAM из swap
6. Прыгает в сохранённое состояние → приложения «продолжают»
```

### Почему hibernate «не идеален»

| Проблема | Детали |
|----------|--------|
| **Медленно** | 64 ГБ записи даже на NVMe ~ 30–90 сек + чтение обратно |
| **Нужен swap ≥ RAM** | zram-своп не подходит (не переживает перезагрузку) |
| **NVIDIA — отдельная история** | GPU-состояние, VRAM, исторические баги пробуждения |
| **Двойная загрузка** | Образ чувствителен к деталям железа и ядра |
| **Старение** | Каждая загрузка с диска — новый риск (образы не совместимы между ядрами) |

## 3. Факты с этой машины (checked ✅)

Что реально проверено на системе 2026-08-21:

```text
/sys/power/state  =  freeze mem disk        ← kernel ПОДДЕРЖИВАЕТ hibernate
/sys/power/disk   =  [platform] shutdown reboot suspend test_resume
/proc/cmdline     =  mem_sleep_default=s2idle   (нет resume= → hibernate НЕ настроен)
swap              =  /dev/zram0 31,3G           (zram не переживает reboot)
CONFIG_HIBERNATION = y, COMP_LZO = y             (LZO-сжатие в ядре есть)
image_size        =  26,7 ГБ                    (лимит образа; RAM 64 ГБ)
CRIU              =  /usr/bin/criu               (уже установлен!)
systemd           =  259                         (умеет suspend-then-hibernate)
openrc/tlp        =  off / off
```

**Вывод: на этой машине hibernate технически возможен, но не настроен, а zram-своп делает классический подход неудобным.**

## 4. Проблемы hibernate именно здесь

### 4.1 64 ГБ RAM → медленно
Даже с сжатием LZO в ядре, 64 ГБ «в сухом виде» сжимаются до ~10–20 ГБ. Это быстрее, но всё равно минуты.

### 4.2 zram — не переживает выключение
```text
/dev/zram0 содержимое живёт в RAM → при выключении СТИРАЕТСЯ.
Hibernate пишет образ в swap → должно пережить выключение.
Решение: файл подкачки на диске (swapfile) вместо zram.
Но: с 64 ГБ RAM swap почти не нужен — zram это «страховка».
```

### 4.3 NVIDIA Wayland
Исторически NVIDIA+x11- сессии страдали от сбоев resume (пропадал сигнал, чёрный экран из-за багов DRM/KMS). У R555+ драйверов стало лучше, но hibernate через swap на zram всё равно не работает без файла подкачки на диске.

### 4.4 Двойное зажигание
Образ гибернации привязан к ядру. При обновлении ядра (CachyOS обновляет ядро часто) старый образ бесполезен — если после обновления попытаться восстановиться из старого образа, ядро либо откажется, либо поведение будет непредсказуемым.

## 5. Альтернативы «получше гибернации»

### 5.1 s2idle — уже используется ✅
```text
freeze userspace → CPU спит → всё просыпается за 1–2 секунды
RAM живёт → состояние сохраняется мгновенно
Ограничение: RAM потребляет энергию, офисный ПК «спит»
```
**Плюс:** мгновенное пробуждение, ноль риска.
**Минус:** нужен электропитание (не защита от пропажи тока).

### 5.2 Гибридный сон (suspend-then-hibernate) ⭐
```text
systemctl suspend-then-hibernate
├── сразу: s2idle (быстрое пробуждение)
├── через N минут отдыха: автоматический hibernate
└── при потере питания дольше N: образ на диске
```
**Лучшее из двух миров.** Можно настроить через `/etc/systemd/sleep.conf`:
```ini
[Sleep]
HibernateDelaySec=1800   # через 30 мин сна → перейти в hibernate
```

### 5.3 Сжатая гибернация (LZO) ⭐
Ядро уже собрано с `CONFIG_HIBERNATION_COMP_LZO`:
```text
64 ГБ RAM → LZO-сжатие → ~10–20 ГБ на диске
```
Требуется swap-файл на диске и `resume=` в cmdline. Это **не «лучше» hibernate, а более быстрый hibernate**.

### 5.4 CRIU — чекпоинты процессов (уже установлен!) ⭐⭐⭐
**Не гибернация системы, а гибернация работы.**
```text
criu dump -t PID    → заморозить процесс, сохранить дамп
criu restore -d     → продолжить процесс (даже после полной перезагрузки!)
```
Пример для tmux/сессии:
```bash
# Сохранить состояние процесса
criu dump -t $(pgrep -f "kate") -D /srv/checkpoints/kate --shell-job

# После перезагрузки — продолжить
criu restore -D /srv/checkpoints/kate --shell-job
```
**Даёт то, что хочет пользователь:** «продолжить с того же состояния» для приложений, независимо от системного сна.

### 5.5 Fast-boot (гибернация при выключении, Windows-стиль)
```text
Вы выключаете → ядро не выключается, а «спит» на диск
Вы включаете → загрузка в 5–10 сек вместо 30+
```
Реализовано в systemd-boot + система «boot counting». Риски те же, что у hibernate (NVIDIA, обновления ядра).

### 5.6 UPS + s2idle ⭐
Самый «честный» ответ для десктопа:
```text
s2idle (мгновенный сон) + ИБП на 10–30 минут
├── кратковременное пропадание тока → s2idle переживает
├── долгое → USB-демон даёт 5-минутный хвост
└── ИБП сигналит → systemctl hibernate, парк-система
```
**Это и есть «гаснет при пропаже питания, возобновляется как ни в чём не бывало» — на уровне физики.** RAM под ИБП живёт, s2idle просыпается мгновенно.

### 5.7 Снапшоты Btrfs + быстрая загрузка
```text
Btrfs снапшот перед выключением (snapper)
├── «состояние» = снапшот ФС + закладки приложений
└── после загрузки: восстановить сессии через tmux-resurrect / browser
```
Это «логическое» восстановление, а не «машинное» — но для рабочих задач почти неотличимо.

|--------|----------------------|---------------------------|-----------|-------------|--------|

## 7. Что реалистично для SEOS QST

### Рекомендуемая композиция (без риска для загрузки)

```text
┌─────────────────────────────────────────────────────────┐
│ SEOS QST: «спит как ни в чём не бывало»                 │
│                                                         │
│ 1. s2idle — ежедневный сон (уже включён)                │
│ 2. suspend-then-hibernate — долгий сон → лёгкий hibernate│
│ 3. CRIU — чекпоинты рабочих сессий (tmux/kate/терминал) │
│ 4. Btrfs снапшоты — точка отката перед выключением      │
│ 5. (опция) UPS — защита питания, чтобы s2idle жил       │
└─────────────────────────────────────────────────────────┘
```

### Что НЕ трогаем сейчас
- Классический hibernate с `resume=zram` — бесполезен (zram не переживает)
- Fast-boot — высокий риск с NVIDIA, не стоит

### Следующие шаги (безопасные, по одной за раз)
1. Настроить `suspend-then-hibernate` через `/etc/systemd/sleep.conf` + swap-файл на NVMe
2. Попробовать CRIU-чекпоинт терминальной сессии (уже установлен!)
3. Настроить snapper-снапшоты перед выключением (Btrfs, кстати, уже используется)

---

**Итог:**
> «Лучше hibernate» — это не один механизм, а **композиция**: s2idle для мгновенного сна + CRIU для чекпоинтов работы + btrfs снапшоты для страховки + (опционально) ИБП для защиты питания. Классический hibernate остаётся как страховка для длительного сна через `suspend-then-hibernate`.
